## 1. 引言与目标

### 1.1 文档目的

本文档定义OPC-OS系统架构必须满足的量化约束，为架构设计、技术选型、性能测试和安全审计提供可验证的标准依据。ARD聚焦“架构必须满足什么条件”，与PRD（业务需求）和SRS（功能需求）形成互补。

### 1.2 范围

本文档覆盖OPC-OS四大变现系统（Skill Forge、AI Startup-in-a-Box、Content Engine、Digital Employee Agency）的架构级需求，包括性能、安全、可靠性、可扩展性、兼容性五大质量属性。

### 1.3 质量目标（按优先级排序）

| 优先级 | 质量属性 | 核心目标 |
|---|---|---|
| P0 | 安全隔离 | 多租户数据零交叉，API Key零泄露 |
| P0 | 可靠性 | 月度可用性≥99.5%，插件崩溃自动恢复 |
| P1 | 性能 | Agent首次响应<2s，记忆检索<500ms |
| P1 | 可扩展性 | 支持从单机到K8s的平滑扩展 |
| P2 | 可维护性 | 插件热重载，配置层可回滚 |

## 4. 架构需求

### 4.1 性能需求

| 编号 | 需求 | 量化指标 | 验证方法 | 来源 |
|---|---|---|---|---|
| AR-P01 | 插件加载时间 | 冷启动含10个插件 < 3s | 性能测试 | 用户体验 |
| AR-P02 | Agent首次响应时间 | 用户发送消息到首个token返回 < 2s | 端到端测试 | 用户体验 |
| AR-P03 | 记忆检索延迟 | 10万条记忆库，R@5查询 < 500ms | 基准测试 | 多Agent协作 |
| AR-P04 | 黑板写入延迟 | 并发5个Agent写入 < 100ms | 并发测试 | 黑板模式 |
| AR-P05 | Skill蒸馏耗时 | 单次蒸馏含质量门控 < 5s | 功能测试 | Skill Forge |
| AR-P06 | 多平台分发适配 | 从内容就绪到发布完成 < 30s/平台 | 集成测试 | Content Engine |
| AR-P07 | 计费事件捕获延迟 | 任务完成到计费记录 < 5s | 埋点验证 | RaaS计费 |
| AR-P08 | 搜索响应时间 | 插件市场搜索 < 500ms | 前端性能测试 | Skill Forge |
| AR-P09 | 支付确认时间 | 用户确认支付到订单生效 < 3s | 支付流程测试 | Skill Forge |
| AR-P10 | 团队组建时间 | Orchestrator拉起团队 < 30s | 集成测试 | AI Startup |

**AR-P03补充说明**：记忆检索依赖LanceDB向量检索与SQLite FTS5全文检索的混合查询。R@5的定义为前5条召回结果中至少1条为相关记忆的查询占比。该指标直接影响多Agent协作的上下文质量和任务完成率。

**AR-P04补充说明**：黑板采用SQLite WAL模式，支持并发读、串行写。写入延迟目标在5个Agent并发写入场景下测量，采用乐观锁+版本号仲裁机制处理冲突。

### 4.2 安全需求

| 编号 | 需求 | 量化指标 | 验证方法 | 来源 |
|---|---|---|---|---|
| AR-S01 | API Key加密存储 | AES-256-GCM | 代码审计+渗透测试 | 凭据安全 |
| AR-S02 | 用户密码传输加密 | TLS 1.3 | 网络抓包验证 | 传输安全 |
| AR-S03 | 敏感信息脱敏 | 日志中API Key/密码出现率 = 0 | 日志审查 | 信息保护 |
| AR-S04 | 客户数据隔离 | 客户A无法访问客户B任何数据 | 安全审计+渗透测试 | 多租户隔离 |
| AR-S05 | 插件签名校验 | Ed25519签名，篡改检出率 = 100% | 篡改检测测试 | 插件安全 |
| AR-S06 | OWASP Top 10覆盖 | 全部10项通过安全扫描 | 安全扫描报告 | 应用安全 |
| AR-S07 | DSH_HOME目录权限 | 0700私有目录 | 权限验证脚本 | 数据隔离 |
| AR-S08 | 多租户资源限制 | 单租户CPU/内存不超配额的110% | 资源监控 | 资源隔离 |

**AR-S04补充说明**：多租户数据隔离是Digital Employee Agency的核心安全需求。参考多租户AI平台的三层隔离设计——权限隔离（租户A不能调用租户B的模型应用）、数据隔离（租户A的知识库不能被租户B检索到）、计费隔离（每个租户的成本独立核算、独立出账）。所有数据表强制携带`tenant_id`字段，所有查询自动追加租户过滤条件。

**AR-S08补充说明**：单租户失控Agent可能拖垮整机。采用systemd资源限制（`TasksMax`/`MemoryMax`/`CPUQuota`）进行隔离。超限时该租户请求排队，不影响其他租户。

### 4.3 可靠性需求

| 编号 | 需求 | 量化指标 | 验证方法 | 来源 |
|---|---|---|---|---|
| AR-R01 | 系统可用性 | 30天连续运行可用性 ≥ 99.5% | 监控统计 | 业务连续性 |
| AR-R02 | 插件崩溃恢复 | 自动恢复时间 < 30s | 故障注入测试 | 稳定性 |
| AR-R03 | Session日志持久化 | append-only，写入丢失率 = 0 | 写入验证 | 数据完整性 |
| AR-R04 | 数据备份 | 每小时增量 + 每日全量 | 备份验证 | 灾难恢复 |
| AR-R05 | 计费埋点可靠性 | 埋点丢失率 < 0.1% | 埋点监控 | 计费准确性 |
| AR-R06 | 插件卸载副作用清理 | 所有通过ctx注册的副作用100%撤销 | 卸载测试 | 运行时稳定性 |

**AR-R02补充说明**：DSH插件加载失败的容错机制至关重要——任何一条挂载失败都会带崩整个Profile启动。采用启动健康握手机制：上次启动未健康时自动隔离全部用户插件，保证宿主永远能回来。

**AR-R03补充说明**：DSH采用事件溯源会话模型，所有运行时状态都是Session追加式事件日志的fold/投影派生。崩溃尾部由`interruptedTurnClosers`合成闭合事件恢复，确保零数据丢失。

**AR-R06补充说明**：Cordis的时间可组合性确保插件卸载时副作用可完整回滚。插件注册的事件监听器、服务、资源在卸载时按LIFO顺序自动撤销。通过`ctx.effect()`声明需要手动清理的资源，运行时累积逆操作并在组件退出时按相反顺序恢复。

### 4.4 可扩展性需求

| 编号 | 需求 | 量化指标 | 验证方法 | 来源 |
|---|---|---|---|---|
| AR-E01 | 单机租户容量 | 支持≥10个客户实例 | 部署测试 | 规模扩展 |
| AR-E02 | 容器租户容量 | 支持≥100个容器实例 | 压力测试 | 规模扩展 |
| AR-E03 | K8s Pod容量 | 支持≥1000个Pod | 架构评估 | 大规模部署 |
| AR-E04 | 插件数量扩展 | 支持≥50个插件同时加载 | 加载测试 | 生态扩展 |
| AR-E05 | 并发Agent数量 | 单实例支持≥10个Agent并行 | 并发测试 | 多Agent协作 |
| AR-E06 | 记忆库容量 | 单实例支持≥100万条记忆 | 存储测试 | 长期运行 |

**AR-E01至AR-E03补充说明**：多租户部署需支持三级扩展路径。单机模式（<10客户）通过`$DSH_HOME`根隔离 + 独立OS账号实现。容器模式（10-100客户）通过`dsh-dock`实现独立容器实例。K8s模式（100+客户）通过独立Pod + NetworkPolicy实现强隔离。

**AR-E05补充说明**：DSH的Scope机制允许每个live agent拥有扁平注册层`agent.ctx`，通过`agent.ctx`注册的工具、prompt section、变量只对该agent可见。官方隔离规则强调“Agent A的本地注册绝不进入Agent B的视图”，同一进程可运行多个异构Agent。

## 5. 架构决策

### ARD-001. 插件化扩展策略

| 属性 | 内容 |
|---|---|
| **状态** | 已接受 |
| **背景** | OPC-OS需在DSH之上构建四大变现系统，DSH处于候选版阶段，API可能漂移 |
| **决策** | 所有扩展以Cordis插件形式实现，不修改DSH框架源码。插件通过`ctx`注册能力，通过`inject`声明依赖，通过`ctx.effect()`管理资源生命周期 |
| **备选方案** | (A) Fork DSH源码直接修改；(B) 独立进程通过API调用DSH；(C) 插件化扩展 |
| **理由** | DSH的设计理念是“一切皆插件”，不存在需要打补丁的特权内核。Cordis提供可回滚Effect和响应式Coeffect，确保插件热插拔的安全性。插件化方案可随DSH版本升级平滑迁移 |
| **后果** | 正面：模块化、可热重载、随DSH升级平滑迁移。负面：受限于DSH插件API能力边界 |

### ARD-002. 多Agent协作采用黑板模式

| 属性 | 内容 |
|---|---|
| **状态** | 已接受 |
| **背景** | 四大系统均需多Agent协作，Agent之间需要共享上下文。核心挑战是避免“Agent互相遗忘”导致输出碎片化 |
| **决策** | 采用黑板模式：Orchestrator读写Global Scope，各Agent拥有独立Agent Scope私有记忆，通过共享黑板交换信息。并发写入采用乐观锁+版本号仲裁 |
| **备选方案** | (A) 中心化消息队列；(B) 点对点Agent通信；(C) 黑板模式 |
| **理由** | 黑板模式支持松耦合协作，Agent可独立扩展。DSH的`dsh-team`插件已实现黑板+成员邮箱+共享任务板的完整能力。乐观锁避免分布式锁的复杂性 |
| **后果** | 正面：松耦合、易扩展、支持异构Agent。负面：需要Orchestrator仲裁冲突，增加编排层复杂度 |

### ARD-003. 三级隔离策略

| 属性 | 内容 |
|---|---|
| **状态** | 已接受 |
| **背景** | Digital Employee Agency需要多租户隔离。Profile隔离和文件沙箱是“防误伤”的软边界，挡不住Agent改坏DSH安装目录 |
| **决策** | 采用三级隔离：L1 Profile隔离（日常开发）、L2 `$DSH_HOME`根隔离（多环境/多租户）、L3 容器/Pod隔离（生产部署）。生产环境用独立OS账号运行DSH，`DSH_HOME`指向0700私有目录 |
| **备选方案** | (A) 仅Profile隔离；(B) 仅容器隔离；(C) 三级隔离 |
| **理由** | 三级隔离匹配不同阶段的隔离需求。Profile隔离轻量快速，适合开发阶段；容器隔离提供硬边界，适合生产。多租户AI平台的核心是三层隔离——权限隔离、数据隔离、计费隔离 |
| **后果** | 正面：安全性与开发效率平衡。负面：生产环境部署复杂度增加 |

### ARD-004. 双记忆系统架构

| 属性 | 内容 |
|---|---|
| **状态** | 已接受 |
| **背景** | Skill Forge需要从工具调用中提炼行为模式，Content Engine需要从对话中积累账号人设。两类需求的数据来源和提炼方式不同 |
| **决策** | 采用双记忆系统：Instinct系统（行为记忆）从工具调用观测记录中提炼，存储于`instincts.jsonl`，全局共享；Memory系统（知识记忆）从对话内容中提炼，存储于`memories.jsonl`，项目级隔离 |
| **备选方案** | (A) 单一记忆系统；(B) 双记忆系统 |
| **理由** | 行为模式和知识记忆的提炼逻辑、存储格式、生命周期完全不同。`dsh-plugin-long-term-memory`已实现双系统架构，可直接复用 |
| **后果** | 正面：各系统独立演化，互不干扰。负面：需维护两套存储和检索逻辑 |

### ARD-005. 事件溯源会话模型

| 属性 | 内容 |
|---|---|
| **状态** | 已接受 |
| **背景** | RaaS计费需要可靠的计费凭证。传统方案从日志推算存在丢失风险 |
| **决策** | 采用DSH原生的事件溯源会话模型：所有运行时状态都是Session追加式事件日志的fold/投影派生。计费事件在`agent/pre-step`和`agent/request`两个waterfall插桩点捕获 |
| **备选方案** | (A) 事后从日志推算计费；(B) 独立计费服务；(C) 事件溯源+waterfall插桩 |
| **理由** | 事件溯源确保计费凭证不可篡改。Waterfall插桩点是“接管决策”而非“旁路监听”，可在任务完成时精确捕获计费事件 |
| **后果** | 正面：计费准确性高、可审计。负面：需理解DSH事件模型 |


## 6. 质量场景

### 场景1：多Agent协作任务完成

| 要素 | 描述 |
|---|---|
| **刺激源** | 用户发起“帮我做一个跨境电商独立站” |
| **刺激** | Orchestrator解析目标，拉起调研、建站、文案、营销4个Agent |
| **环境** | 正常运行时，5个Agent并发操作黑板 |

## 8. 术语表

| 术语 | 定义 |
|---|---|
| ARD | Architecture Requirements Document，架构需求文档，定义系统架构必须满足的量化约束 |
| ADR | Architecture Decision Record，架构决策记录，捕获重要架构决策及其上下文和后果 |
| DSH | DeepSeek Harness，DeepSeek官方开源的Agent运行时框架 |
| Cordis | DSH底层的插件框架，提供依赖注入、可逆Effect、类型化事件和Scope隔离 |
| Profile | DSH的具名组装配置，列出叠放的组合包并保存用户patch |
| Bundle | Cordis配置项及其挂载代码的分发格式 |
| Waterfall | Cordis的接管式事件钩子机制，主循环暴露`agent/pre-step`、`agent/request`、`agent/request-error`三个可接管点 |
| Effect | Cordis中描述组件如何改变环境的机制，支持逆操作回滚 |
| Coeffect | Cordis中描述组件需要从环境获得什么，支持依赖动态响应 |
| RaaS | Results as a Service，结果即服务 |
| 黑板模式 | 多Agent共享工作区的架构模式 |
| R@5 | 前5条召回结果中至少1条为相关记忆的查询占比 |
