### 1.2 术语表

| 术语 | 定义 |
|---|---|
| DSH | DeepSeek Harness，DeepSeek官方开源的Agent运行时框架，秉持"一切皆插件"理念，将模型适配器、工具、会话、主循环等全部解耦为可配置、可替换的插件 |

## 2. 业务背景与市场分析

### 2.1 问题陈述

**现状与证据**：独立开发者和一人创业者面临三重困境。第一，时间无法规模化——AI工具虽能提升单次任务效率，但工作流本身无法被封装和复用。第二，单Agent能力边界明显——复杂任务需要多角色协作，但现有工具缺乏原生多Agent编排和记忆共享能力。第三，变现路径单一——多数AI工具仍按席位或调用量收费，与用户实际获得的业务价值脱节。

**影响与代价**：据市场研究，全球AI Agent市场2026年规模为72亿美元，预计2034年达到784亿美元，CAGR为34.8%。与此同时，传统SaaS按席位收费模式正面临根本性挑战——IDC预测到2028年70%的软件供应商将转向按业务结果计费。不抓住这一窗口期，独立开发者将持续在低附加值的"卖时间"模式中循环。

**时机与约束**：DSH v0.1.0-rc.7已提供成熟的插件化底座，Cordis运行时、Profile/Bundle装配机制、Waterfall插桩点等核心能力均已就绪。社区已积累`dsh-team`、`dsh-Visual-Workflow`、`dsh-plugin-long-term-memory`等关键插件，为OPC-OS的开发提供了可复用的基础设施。但DSH仍处于候选版阶段，API存在漂移风险。

### 2.2 市场机会

AI Agent市场处于爆发前夜。全球AI Agent市场从2025年的82.9亿美元增长至2026年的120.6亿美元，CAGR达45.5%。到2026年底，预计40%的企业应用将包含任务特定型Agent。企业采购模式正从"按席位"转向"按结果"，66%的中国企业倾向基于业务成果计费购买AI能力。

### 5.3 插件技术规范

DSH插件是一个导出`apply`函数的TypeScript模块，基于Cordis：通过`name`命名、`inject`声明依赖、`ctx`注册能力、Config schema接受配置。

```typescript
import type { Context } from '@deepseek-ai/cordis'

export const name = 'my-plugin'
export const inject = ['tools']
export const Config = Schema.object({
  greeting: Schema.string().default('Hello'),
})

export function apply(ctx: Context, config: Config) {
  ctx.tools.register(/* 自定义工具 */)
  ctx.effect(() => {
    const timer = setInterval(() => {/* ... */}, 5000)
    return () => clearInterval(timer)
  })
}
```

**自动清理规则**：通过`ctx`注册的任何东西——事件监听、工具、定时器——在插件卸载时都会自动清理。有需要手动清理的资源（比如网络连接），用`ctx.effect()`告诉框架怎么清理。

**Bundle打包结构**：
```
my-plugin/
├── package.json      # 声明 dsh.bundle
├── cordis.patch.yml  # 该组合包贡献的配置层
└── index.js          # 构建产物
```

#### 6.1.2 本能提炼引擎

基于`dsh-plugin-long-term-memory`的**Instinct系统**（行为记忆）。该插件采用双记忆系统架构：Instinct系统从工具调用观测记录中提炼行为模式，存储于`instincts.jsonl`，作用范围为全局。

**蒸馏逻辑**增加**质量门控层**：仅当调用序列满足"重复次数 ≥ 3"且"任务完成质量达标"时触发。蒸馏产物格式：

```yaml
name: "contract-review-skill"
version: "1.2.0"
memory_snapshot:
  - soul: "合同审查专家人格"
  - lesson: "金融合同必须检查利率上限条款"
skill_definition:
  trigger: "用户上传合同PDF"
  tool_sequence: [pdf_reader, clause_extractor, risk_scorer]
  post_conditions: "输出风险评级+逐条修改建议"
```

#### 6.1.3 异常与边界处理

| 异常场景 | 处理策略 |
|---|---|
| 工具调用序列不完整 | 标记为"低置信度"，不触发蒸馏 |
| 蒸馏产物质量不达标 | 提示用户手动编辑Skill定义 |
| 包安装失败（版本不兼容） | 提示兼容性信息，回滚至安装前状态 |
| 支付超时 | 30秒超时自动取消，订单状态回滚 |
| 技能被恶意篡改 | 包签名校验，不通过则拒绝安装 |

#### 6.1.4 数据模型

```

├── packages/           # .dshpkg文件存储

#### 6.2.2 技术实现

**核心依赖`dsh-team`**：在会话中输入`/agent-teams <目标>`，主会话即拉起一支队伍。每位队友有自己的名字、会话和记忆，能互发消息、认领共享任务、往共享黑板写结论。

关键能力：
- **常驻队友**：每位队友有名字、角色和独立记忆
- **成员邮箱**：队友之间直接通信，不必事事经过主会话
- **共享任务列表**：全队认领同一份清单
- **共享工作区**：全队共用黑板 + 每人私有便笺，重启后数据不丢失

┌─────────────────────────────────────┐

└──────────────┬──────────────────────┘
               │
        ┌──────▼──────┐
        │  Blackboard  │  ← SQLite WAL 模式
        │    (黑板)     │    并发读，串行写
        └──┬───┬───┬──┘
           │   │   │
      ┌────▼┐ ┌▼──┐ ┌▼────┐
      │Agent│ │Agent│ │Agent │
      │  A  │ │  B  │ │  C   │
      └─────┘ └────┘ └──────┘
      各自拥有 Agent Scope 私有记忆
```

**记忆作用域链**：

| 层级 | 内容 | 存储位置 | 读写权限 |
|---|---|---|---|
| Global Scope | 业务规则、共享事实 | `$DSH_HOME/shared/blackboard.json` | 所有Agent可读，仅Orchestrator可写 |
| Workflow Scope | 当前任务事件记忆 | SQLite WAL模式 | 参与任务的Agent可读写 |
| Agent Scope | 角色私有记忆 | 各Agent的`long-term-memory`数据库 | 仅该Agent可读写 |

**并发冲突解决**：采用乐观锁机制——Agent写入时携带版本号，Orchestrator检测到版本冲突时，按"时间戳+置信度"优先级仲裁。

#### 6.2.3 异常与边界处理

| 异常场景 | 处理策略 |
|---|---|
| 目标解析失败 | 降级为手动选择角色模板 |
| 某Agent执行超时 | 自动重试1次，失败后标记任务为"需人工介入" |
| 黑板写入冲突 | 乐观锁仲裁，保留高优先级写入 |
| Token消耗超预算 | 阈值告警（80%时），超支拦截（100%时） |
| 团队成员全部空闲 | 自动缩减团队规模或提示用户重新分配任务 |

#### 6.4.2 多租户隔离架构

**隔离级别定义**：

| 级别 | 方案 | 适用场景 | 隔离强度 |
|---|---|---|---|
| L1 | Profile隔离 | 日常插件开发 | 软隔离，防误伤 |
| L2 | `$DSH_HOME`根隔离 | 多环境/多租户 | 数据隔离 |
| L3 | 容器/Pod隔离 | 生产部署/公网多租户 | 硬隔离，防改坏 |

**单机模式**（< 10客户）：每个客户使用独立的`$DSH_HOME`根，差异只在patch内容。

**容器模式**（10-100客户）：参考`dsh-dock`的实现，一个容器就是一个独立DSH实例，拥有独立`DSH_HOME`（凭据/会话/设置/存储）、固定端口、容器内默认工作区。

**K8s模式**（100+客户）：每用户独立Pod，数据为PostgreSQL（CloudNativePG），Pod网络+SecurityContext+NetworkPolicy强隔离，控制面3副本+leader election。

**公网多租户模式**：参考`dsh-server-login`架构——每用户独立系统账号`dsh-<name>`，`DSH_HOME`指向其0700私有目录，配合systemd资源限制（`TasksMax`/`MemoryMax`/`CPUQuota`）防止单个租户的失控Agent拖垮整机。

#### 6.4.3 RaaS计费埋点

在DSH工具层埋设计费事件，利用`agent/pre-step`和`agent/request`两个waterfall插桩点捕获。`agent/pre-step`是每个step的入口检查点，监听器可以放行或替换消息。

```typescript
onTaskComplete({
  taskId: "task_20260915_001",
  agentId: "customer-service-acme",
  resolution: "resolved",  // resolved | escalated
  tokensUsed: { prompt: 12500, completion: 3200 },
  durationMs: 45000
})
// resolution=resolved → 计费¥2.50
// resolution=escalated → 免费，失败记忆写入lesson层
```

#### 6.4.4 客户知识自积累

基于`dsh-persona-memory`的后台自动学习机制（每10轮对话自动复习并提取持久事实）。核心实现三个子模块：

| 模块 | 触发条件 | 写入目标 | 数据格式 |
|---|---|---|---|
| 纠正检测 | 人工客服介入纠正AI回答 | lesson层 | `{original, correction, context, timestamp}` |
| 失败记忆 | LLM调用失败或任务转人工 | lesson层 | `{failure_scenario, correct_path, timestamp}` |
| 业务规则蒸馏 | 从历史工单中提取 | fact层 | `{rule, confidence, source, timestamp}` |

#### 6.4.5 异常与边界处理

| 异常场景 | 处理策略 |
|---|---|
| 客户DSH实例崩溃 | 自动重启，会话状态从Session日志恢复 |
| API Key失效 | 告警通知管理员，暂停该客户服务 |
| 计费埋点丢失 | 从Session事件日志回溯补录 |
| 转人工率异常升高 | 触发告警，人工审查AI回答质量 |
| 多租户资源争抢 | systemd资源限制隔离，超限时排队 |
